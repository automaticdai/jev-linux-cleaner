# jev-cleaner

A Linux disk cleaner that judges the leftovers no rule list covers.

Rule-based cleaners only know the paths someone put in a list. jev-cleaner
enumerates candidate directories, hands each one to [Jev](https://docs.typesafe.ai)
as a small set of typed questions, and reports what it found. Four directories
in one `~/.cache` show why that matters:

| Directory | Size | What deletion costs |
| --- | --- | --- |
| `uv` | 5.7 GB | a slower next resolve, automatic |
| `ms-playwright` | 1.9 GB | broken until you run `playwright install` |
| `huggingface` | 469 MB | a long model re-download, automatic |
| `mesa_shader_cache` | 1.6 MB | nothing noticeable |

`rm -rf ~/.cache` treats all four the same. jev-cleaner does not.

## It never deletes

v1 removes nothing. It writes a report, a run artifact, and a `plan.sh` that it
does not execute. You read the script and run it yourself.

## Install

```bash
pip install -e .
export TYPESAFE_API_KEY=...   # from https://console.typesafe.ai/
```

## Use

```bash
jev-cleaner scan                  # walk your home, judge, write a run
jev-cleaner scan --system         # also scan system locations, through sudo
jev-cleaner scan --containers     # also report reclaimable docker space
jev-cleaner scan --dry-run        # print one state, make no API calls
jev-cleaner report --tier clean   # render a stored run; no network
jev-cleaner report --policy my.yaml   # re-tier a stored run under new thresholds
jev-cleaner explain ~/.cache/uv   # every probability behind one verdict
jev-cleaner plan                  # write plan.sh (never executed)
jev-cleaner disagree              # rows where Jev and the rule baseline differ
```

A full scan of a home directory is roughly a million input tokens, about four
cents at Jev's current price.

## Tiers

| Tier | Meaning |
| --- | --- |
| `clean` | regenerated by the program itself; deleting it costs nothing you would notice |
| `costly` | reclaimable, but restoring it takes a command, a download, or a new login |
| `orphan` | the owning software appears to be gone, and the directory has sat idle |
| `review` | the model was not confident enough to place it; look yourself |
| `keep` | user content, settings, or program files |
| `denied` | the safety floor held it back; never judged, never offered |

## The safety floor

Dropped in code before anything is sent or judged, and never recommended:
`/etc`, `/boot`, `/usr`, `/bin`, `/sbin`, `/lib`, `/dev`, `/proc`, `/sys`,
`/run`, `/opt`; `~/.ssh`, `~/.gnupg`, `~/.password-store`, keyrings, `~/.aws`,
`~/.kube`; `~/Documents`, `~/Desktop`, `~/Pictures`, `~/Videos`, `~/Music`;
anything with a `.git` above it; anything modified in the last 15 minutes;
anything passed to `--protect`. Symlinks are never followed and mount
boundaries are never crossed.

Privileged scanning runs `jev_cleaner/probe.py` under `sudo`: a stdlib-only,
read-only walker that prints JSON and exits. The main process never runs as
root, and the probe never sees the API key.

## What the model is and is not asked

Jev answers seven questions per directory, all in one request. Six are about
what is in the directory; none asks whether to delete it. That is policy, and
policy lives in `policy.py`, so changing a threshold re-tiers a whole stored run
without a single new request.

Two findings from building this, both visible in the git history:

- Telling the model that `~/.cache` "holds data an application can regenerate"
  made it adopt that conclusion over the evidence, rating 2 GB of browser
  binaries as costless to delete. The state now says where a directory is and
  nothing about what that implies.
- The five-level loss Score does not separate a shader cache from a browser
  download; both come back at ~1.0. Two literal questions about what the
  directory *contains* separate them cleanly (0.06 versus 0.81), so policy
  derives restore effort from those instead.

## Evaluation

`pytest -m eval` scores the latest run against hand labels in
`tests/fixtures/labels.json`.

**Current: 79% agreement over 29 labelled directories — below the 80% bar, so
the eval fails.** No directory labelled `keep` was offered for deletion; all six
mismatches are the tool routing something to `review` that a person would have
tiered confidently. The tool is safe but not yet decisive, which is the reason
v1 does not delete.

The shipped labels were written on one machine and, honestly, after seeing one
run, so treat them as a starting point: replace them with your own before
trusting the number.
